# ChenHai（海琛）

**證據探查與評估 Skill（Evidence Exploration and Evaluation Skill）**

> 海琛負責判斷：我們現在知道得夠不夠。
>
> 它也負責讓證據在邊界明確、命名清楚、可審計的環境中被處理。

**開發狀態：Reserved / Planned（已預留 / 規劃中）；證據約束 Harness MVP 已實作**

本倉庫是本 Skill 的正式（canonical）未來實作倉庫。
其初始提交用於在實作開始之前，先固定 Skill 契約、架構邊界與計畫中的公開介面。
第一個最小執行期切片——證據約束 Harness MVP——已在 `skills/chenhai_harness/`
下實作。證據充分性判斷職責仍停留在設計階段，尚未實作。

## 它是什麼

ChenHai 是 SeaFlow 中負責**證據探查與評估**的 Skill。
它評估當前已掌握的證據是否足夠，識別尚未解決的證據缺口，
並為編排層產出重試 / 補取建議。

## 為什麼需要它

檢索流程可以回傳結果，而待證事項仍然缺乏支撐。必須有人判斷覆蓋度、
指出不充分之處、並說明應當重試什麼。ChenHai 的存在，是為了讓這一判斷
顯式、可檢視，並與檢索、最終法律推理相互分離。

## 核心職責

- 證據覆蓋度評估；
- 不充分性偵測；
- 檢索風險 / 召回風險訊號；
- 在存在 qrels 時的基準精確率 / 召回率評估；
- 在缺乏完整 ground truth 時的執行期覆蓋度代理指標；
- 識別尚未解決的證據缺口；
- 為編排層產出重試 / 補取建議。

擴充職責 —— 證據約束（evidence discipline）：

- 約束證據如何被組織與處理；
- 約束證據產物的命名；
- 建構並校驗受控評估工作區；
- 在正式證據任務開始前校驗證據處理環境是否規範、可審計。

原有的「充分性判斷」職責保持不變。證據約束是對它的擴充，而不是重新定義。

## 證據邊界

ChenHai **不**：

- 自行檢索證據；
- 編造缺失證據；
- 靜默填補缺口；
- 作出最終的規範判斷或法律判斷；
- 直接改動正式證據；
- 充當通用檔案管理器；
- 充當通用工作流程引擎；
- 重新命名與證據任務無關的任意使用者檔案；
- 僅憑命名策略決定實質內容；
- 製造虛假的審計證據；
- 事後重建缺失的歷史證據。

架構規則：ChenHai 偵測不充分並請求補取；XianHai 決定時序與補取編排；
檢索類 Skill 負責實際檢索。

## 證據約束 Harness（Evidence Discipline Harness）

ChenHai 同時約束兩件事：證據是否**充分**，以及證據被處理的環境是否**規範**。
後者在本倉庫中稱為證據約束 Harness：它是一層證據層面的約束，而不是通用檔案系統功能，
也不是企業級編排框架。

具體而言，ChenHai 可以約束：可用證據的範圍、證據處理任務發生的位置、期望產出哪些產物、
這些產物如何命名、允許或禁止寫入與存取什麼，以及由此形成的證據狀態日後如何被審計。

### 語意化產物命名

證據產物應當可以按主題與產物角色被識別。ChenHai 可以定義或執行命名規則，優先採用
`<topic>_<artifact-role>.<ext>` 形式；在情境需要時，採用
`<case-or-task>_<topic>_<artifact-role>.<ext>` 形式。

示意形態（並非已凍結的約定）：

```
collision_liability_evidence_ledger.csv
missing_authority_assessment.md
route_source_inventory.json
port_law_conflict_matrix.csv
```

應當避免 `output1.txt`、`result_final.md`、`data_new.json`、`test2.csv` 這類含混標籤：
它們沒有傳達主題、角色或來源，只會讓後續審計更困難。

命名約定預計仍會演進；本階段不凍結任何剛性的通用檔名文法。架構層面的要求是：
檔名應當傳達主題與證據 / 產物角色、避免無意義的泛化標籤、提升可追溯性與後續可審計性，
並在可行時保持確定性。

ChenHai 約束產物的命名。它**不會**僅僅為了滿足命名規則而編造檔案內容。

### 受控證據工作區

在正式的證據任務開始之前，ChenHai 可以協助建構或校驗一個面向特定任務的受控環境——
概念上就是「先把考場搭好」。該環境明確：允許的輸入、凍結的證據來源、可寫輸出位置、
禁止存取的路徑、期望的產物、證據清單、任務特有約束、評估規則、完整性校驗與失敗條件。

概念順序如下：

```
定義任務
    ↓
定義證據邊界
    ↓
建構受控工作區
    ↓
凍結 / 確定允許的輸入
    ↓
定義期望產出
    ↓
執行任務
    ↓
評估證據的充分性與完整性
```

其目的是減少：證據污染、對禁入材料的意外存取、來源含混、失控寫入、陳舊或無關情境、
事後重建，以及評估洩漏。

計畫中的概念元素 —— 這裡作為意圖記錄。MVP 目前已實作語意化命名策略、受控工作區規範、
期望產物宣告、完整性門檻與完整性校驗；其餘元素仍只是意圖：

- ControlledEvidenceWorkspace（受控證據工作區）
- 輸入邊界
- 輸出邊界
- 證據清單
- 期望產物集合
- 語意化命名策略
- 讀寫邊界
- 凍結來源宣告
- 完整性校驗
- 完整性門檻
- 失敗 / 拒答狀態

除該 Harness MVP 之外，沒有設計任何進一步的執行期類別、套件、schema 或沙箱 API，
也不聲稱它們已經存在。MVP 本身沒有實作任何沙箱 API，也不作此聲明。

### 證據約束 Harness MVP（Evidence Discipline Harness MVP）

Harness 的第一個最小執行期切片已經實作，位於 [`skills/chenhai_harness/`](./skills/chenhai_harness/)：
一個小型、確定性的檔案系統 Harness，**不依賴任何 LLM**，不做檢索、不做語意推斷，
也不判斷產物內容在實質上是否正確。它實作了語意化命名策略、受控工作區規範、
期望產物宣告、完整性門檻與完整性校驗。

四個操作為 `init`、`stage`、`place`、`validate`，結果為 `PASS`、`INCOMPLETE` 或
`REFUSE`。**本 MVP 不是作業系統沙箱**：它不能阻止外部模型、行程或使用者讀寫任意路徑，
也沒有實作任何檔案系統隔離。

完整的實作說明（操作、TaskSpec、命名慣例、退出碼與沙箱限制）見英文
[README.md](./README.md) 與簡體中文 [README.zh-CN.md](./README.zh-CN.md)；
本文件目前只描述 Skill 契約。

### Harness 的邊界

該能力約束的是證據處理方式，而不是製造證據。

ChenHai 可以定義評估的「考場」，但它不自行檢索證據，不掌握時序編排，
不掌握溯源圖語意，也不會變成通用檔案管理器或通用工作流程引擎。

## 它如何嵌入 SeaFlow

```
證據取得 / 資產
    ↓
ShanHai / LuoHai / WenHai / 未來視覺證據
    ↓
XianHai
時序組織 / 斷層 / 複核
    ↕
JueHai
關係 / 溯源路徑
    ↓
ChenHai
覆蓋度 / 不充分性 / 評估
    ↓
證據不充分時發出補取請求
```

以上是**架構關係**，不是已實作的耦合。當前階段，這些 Skill 之間並不存在硬性執行期依賴。

各 Skill 邊界保持清晰：

| Skill | 負責範圍 |
| --- | --- |
| ShanHai | 檢索 / 結構化法律文本證據 |
| LuoHai | 處理結構化 / 表格類證據 |
| WenHai | 登記與保存文件類資產 |
| XianHai | 按時間組織證據，管理時序斷層 / 複核 |
| JueHai | 透過圖關係與溯源路徑連接證據 |
| ChenHai | 評估充分性，**並**約束證據評估環境 |

ChenHai 可以定義評估環境，但它不檢索證據，不掌握時序編排，不掌握溯源圖語意，
也不會變成通用檔案管理器。

引入 Harness 後的概念流程：

```
證據進入
    ↓
ChenHai 校驗環境是否規範
    ↓
證據任務在受控邊界內執行
    ↓
產物採用語意化 / 可追溯命名
    ↓
ChenHai 評估覆蓋度 / 不充分性
    ↓
如有需要，請求補取
```

證據充分性判斷職責尚未實作。概念性介面與路線圖見 [SKILL.md](./SKILL.md)。
