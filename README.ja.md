# ChenHai（海琛）

**証拠探查・評価 Skill（Evidence Exploration and Evaluation Skill）**

> 海琛（ChenHai）は「今の証拠で足りているか」を問う。
>
> また、証拠が境界の明確な、命名の整った、監査可能な環境で扱われることを支えます。

**開発ステータス：Reserved / Planned（予約済み / 計画中）**

本リポジトリは、本 Skill の正式（canonical）な将来実装リポジトリです。
現段階では意図的に「ドキュメント優先・コード最小」としています。
初期コミットは、実装開始前に Skill の契約、アーキテクチャ上の境界、
および計画中の公開インターフェースを固定するためのものです。

## これは何か

ChenHai は SeaFlow において**証拠の探查と評価**を担う Skill です。
現在保持している証拠が十分かどうかを評価し、未解決の証拠ギャップを特定し、
オーケストレーション層に向けた再試行 / 再取得の推奨を生成します。

## なぜ必要なのか

検索パイプラインが結果を返しても、対象となる事項が依然として裏付けを欠くことはあります。
カバレッジを判断し、不十分さを名指しし、何を再試行すべきかを示す主体が必要です。
ChenHai は、その判断を明示的かつ検証可能にし、検索や最終的な法的推論から
分離するために存在します。

## 主要な責務

- 証拠カバレッジの評価；
- 不十分性の検出；
- 検索リスク / 再現率リスクのシグナル；
- qrels が存在する場合のベンチマーク適合率 / 再現率の評価；
- 完全な ground truth が得られない場合の実行時カバレッジ代理指標；
- 未解決の証拠ギャップの特定；
- オーケストレーション層に向けた再試行 / 再取得の推奨の生成。

拡張された責務 —— 証拠の規律（evidence discipline）：

- 証拠がどのように整理・処理されるかの規律；
- 証拠成果物の命名の規律；
- 統制された評価ワークスペースの構築と検証；
- 正式な証拠タスクの開始前における証拠処理環境の検証。

従来の「十分性の判断」という責務は維持されます。証拠の規律はその拡張であり、
再定義ではありません。

## 証拠の境界

ChenHai は次を行い**ません**：

- 自ら証拠を検索すること；
- 欠落した証拠を捏造すること；
- ギャップを黙って埋めること；
- 最終的な規範判断または法的判断を下すこと；
- 正式な証拠を直接変更すること；
- 汎用のファイルマネージャとして振る舞うこと；
- 汎用のワークフローエンジンとして振る舞うこと；
- 証拠タスクと無関係な任意のユーザーファイルを改名すること；
- 命名ポリシーだけで実質的な内容を決めること；
- 虚偽の監査証跡を作成すること；
- 欠落した過去の証拠を事後に再構成すること。

アーキテクチャ上の規則：ChenHai が不十分性を検出して再取得を要求し、
XianHai が時系列および再取得のオーケストレーションを決定し、
検索系 Skill が実際の検索を行います。

## 証拠規律 Harness（Evidence Discipline Harness）

ChenHai は二つのことを同時に制約します。証拠が**十分**かどうか、そして証拠が処理される
環境が**規律あるもの**かどうかです。後者を本リポジトリでは証拠規律 Harness と呼びます。
これは証拠レイヤーの制約であり、汎用ファイルシステム機能でも、エンタープライズ向けの
オーケストレーションフレームワークでもありません。

具体的には、ChenHai は次を制約できます：利用可能な証拠の範囲、証拠処理タスクが行われる場所、
どのような成果物が期待されるか、それらの成果物の命名、書き込み・アクセスの可否、
そして結果としての証拠状態が後からどのように監査されるか。

### 意味に基づく成果物の命名

証拠成果物は、主題と成果物の役割によって識別できるべきです。ChenHai は命名規則を定義または
適用できます。優先する形式は `<topic>_<artifact-role>.<ext>`、文脈上必要な場合は
`<case-or-task>_<topic>_<artifact-role>.<ext>` です。

例示的な形（凍結された規約ではありません）：

```
collision_liability_evidence_ledger.csv
missing_authority_assessment.md
route_source_inventory.json
port_law_conflict_matrix.csv
```

`output1.txt`、`result_final.md`、`data_new.json`、`test2.csv` のような曖昧なラベルは
避けるべきです。これらは主題・役割・来歴を伝えず、後続の監査を難しくするだけです。

命名規則は今後も発展する見込みです。本段階で固定的な汎用ファイル名文法を凍結しません。
アーキテクチャ上の要件は、ファイル名が主題と証拠 / 成果物の役割を伝えること、無意味な
汎用ラベルを避けること、追跡可能性と後続の監査可能性を高めること、そして実務上可能な範囲で
決定的であることです。

ChenHai は成果物の命名を制約します。命名規則を満たすためだけにファイル内容を捏造することは
**ありません**。

### 統制された証拠ワークスペース

正式な証拠タスクの前に、ChenHai はタスク固有の統制された環境の構築または検証を支援できます。
概念としては「まず試験会場を整える」ことに相当します。この環境は、許可された入力、凍結された
証拠ソース、書き込み可能な出力先、禁止されたパス、期待される成果物、証拠マニフェスト、
タスク固有の制約、評価規則、完全性検査、失敗条件を明確にします。

概念上の順序は次のとおりです：

```
タスクを定義
    ↓
証拠の境界を定義
    ↓
統制されたワークスペースを構築
    ↓
許可された入力を凍結 / 特定
    ↓
期待される出力を定義
    ↓
タスクを実行
    ↓
証拠の十分性と完全性を評価
```

目的は次を減らすことです：証拠の汚染、禁止された資料への偶発的なアクセス、来歴の曖昧さ、
統制されない書き込み、古いまたは無関係な文脈、事後の再構成、評価の漏洩。

計画中の概念要素 —— 意図としての記録であり、**未実装**です：

- ControlledEvidenceWorkspace（統制された証拠ワークスペース）
- 入力境界
- 出力境界
- 証拠マニフェスト
- 期待される成果物セット
- 意味に基づく命名ポリシー
- 読み書きの境界
- 凍結ソース宣言
- 完全性検査
- 完全性ゲート
- 失敗 / 拒否の状態

本段階では、実行時のクラス、パッケージ、スキーマ、サンドボックス API は一切設計しておらず、
それらが存在するとも主張しません。

### 証拠規律 Harness MVP（Evidence Discipline Harness MVP）

Harness の最初の最小ランタイム実装が [`skills/chenhai_harness/`](./skills/chenhai_harness/)
に追加されました。小さな決定論的ファイルシステム Harness であり、**LLM 依存は一切なく**、
検索も意味推論も行わず、成果物の内容が実質的に正しいかどうかも判断しません。
意味に基づく命名ポリシー、統制されたワークスペース仕様、期待される成果物の宣言、
完全性ゲート、完全性検査を実装しています。

4 つの操作は `init`、`stage`、`place`、`validate` で、結果は `PASS`、`INCOMPLETE`、
`REFUSE` のいずれかです。**本 MVP は OS サンドボックスではありません**。外部のモデル、
プロセス、利用者が任意のパスを読み書きすることを防ぐものではなく、ファイルシステムの
隔離は実装していません。

実装の詳細（操作、TaskSpec、命名規則、終了コード、サンドボックスではないという制約）は
英語版 [README.md](./README.md) と簡体字中国語版
[README.zh-CN.md](./README.zh-CN.md) を参照してください。本ファイルは現時点では
Skill の契約のみを記述しています。

### Harness の境界

この能力が制約するのは証拠の扱い方であり、証拠を製造することではありません。

ChenHai は評価の「試験会場」を定義できますが、自ら証拠を検索せず、時系列の
オーケストレーションを掌握せず、来歴グラフの意味論を掌握せず、汎用のファイルマネージャや
汎用のワークフローエンジンになることもありません。

## SeaFlow への組み込み方

```
証拠の取得 / アセット
    ↓
ShanHai / LuoHai / WenHai / 将来の視覚証拠
    ↓
XianHai
時系列の編成 / ギャップ / 再確認
    ↕
JueHai
関係 / 来歴パス
    ↓
ChenHai
カバレッジ / 不十分性 / 評価
    ↓
証拠が不十分な場合の再取得リクエスト
```

これは**アーキテクチャ上の関係**であり、実装済みの結合ではありません。
現段階で、これらの Skill 間にハードな実行時依存は存在しません。

各 Skill の境界は明確に保たれます：

| Skill | 担う範囲 |
| --- | --- |
| ShanHai | 法的テキスト証拠の検索 / 構造化 |
| LuoHai | 構造化証拠 / 表形式証拠の扱い |
| WenHai | 文書資産の登録と保存 |
| XianHai | 証拠の時系列編成、時系列ギャップ / 再確認の管理 |
| JueHai | グラフ関係と来歴パスによる証拠の接続 |
| ChenHai | 十分性の評価、**および**証拠評価環境の制約 |

ChenHai は評価環境を定義できますが、自ら証拠を検索せず、時系列のオーケストレーションを
掌握せず、来歴グラフの意味論を掌握せず、汎用のファイルマネージャになることもありません。

Harness 導入後の概念的な流れ：

```
証拠が入る
    ↓
ChenHai が環境の規律を検査
    ↓
証拠タスクが統制された境界内で実行される
    ↓
成果物は意味に基づく / 追跡可能な命名を用いる
    ↓
ChenHai がカバレッジ / 不十分性を評価
    ↓
必要に応じて再取得を要求
```
